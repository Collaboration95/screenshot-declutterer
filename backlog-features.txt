Screenshot Declutterer — Feature Backlog
==========================================

Features under active planning or development.
Status: planned | in-progress | done


SCOPE EXPANSION
---------------

[x] FE-001  Support non-PNG screenshots
           macOS also produces .jpg screenshots and screen recordings.
           Expand SCREENSHOT_GLOB to match multiple extensions and
           handle MIME types accordingly.

[ ] FE-002  Recursive / subdirectory scanning
           Currently scans top-level ~/Desktop only. Add option to
           recurse into subdirectories and surface nested screenshots.

[ ] FE-003  Tracking folders (configurable source folders)
           Scan user-chosen directories in addition to ~/Desktop (e.g.
           ~/Downloads, dev scratch dirs). LOGGED as GitHub issue #70 —
           spec TBD: folder-picker UI, source tagging on cards, filename
           collision handling, persistence in settings.json.


NEW ACTIONS
-----------

[ ] FE-004  Move to folder
           Add a fourth action alongside Keep/Trash that lets users
           move screenshots into a chosen destination folder.

[ ] FE-005  Bulk rename
            Rename screenshots based on patterns (date, sequential
            numbering, custom prefix) directly from the UI.
            NOTE: Single-file rename is now implemented via the
            Rename button on each card. Bulk pattern-based rename
            remains a future enhancement.

UX IMPROVEMENTS
---------------

[x] FE-010  Inline filename display & lightbox rename (done — shipped 0.2.0)

            Click to edit inline — no modal needed. Reuses existing
            POST /api/rename endpoint. No backend changes required.
            Design doc: docs/design-fe010-inline-rename.md

[ ] FE-008  Sort and filter by date range, file size, or screen region
           Let users narrow down visible screenshots before sorting.

[ ] FE-009  Persistent user preferences
           Remember default sort order, column widths, and other
           settings across sessions.


SMARTER FEATURES
----------------

[x] FE-011  Auto-categorization (done — shipped 0.4.0 as keyword-based
           category hints; on-device ML remains aspirational)
           Current impl: Keep/Trash hints via keyword overlap with past
           decisions (suggest_category) + colored card borders.

[ ] FE-012  Screenshot clustering
           Group screenshots by application or window to make bulk
           triage faster.

[x] FE-016  LLM-powered smart rename (done — shipped 0.4.0: per-card
           ✨ Suggest, Suggest All + progress, accept/reject/edit badges,
           /api/suggest-names, /api/accept-suggestion, /api/reject-suggestion,
           Ollama circuit breaker + /api/ollama/health)
           Integrate a local LLM (Gemma via Ollama or MLX) to
           generate plausible screenshot names. Requires persistent
           file memory (FE-017) to avoid re-processing.
           Design doc: docs/design-llm-rename-prerequisites.md
           NOTE: default vision model (gemma4:e2b) is too heavy for local
           hardware — OCR-hybrid pipeline (FE-019) is the follow-up.

[x] FE-017  Persistent file memory store (done — all phases shipped in 0.4.0:
           1A memory module, 1B app.py integration (PR #64), 1C frontend
           fingerprint + memory_status data attributes)
           Track screenshot identity across sessions using metadata
           fingerprints. Foundation for FE-016 (LLM rename) and
           FE-011 (auto-categorization).
           Design doc: docs/design-llm-rename-prerequisites.md

LLM & AI
--------

[ ] FE-018  LLM benchmark suite — Ollama vs MLX vs alternatives        [P1][M]
           Systematic perf + quality testing of candidate models/runtimes
           for the screenshot-rename task, using tools/eval-screenshot-names.py.
           Output: a repeatable comparison table — latency, tokens/sec, RAM/VRAM
           footprint, and rename quality score on the same test set.
           Runtime candidates: Ollama (CPU/GPU), MLX (Apple Silicon),
           llama.cpp (llama-cli), CoreML (via coremltools), ONNX Runtime.
           Model candidates: qwen2.5:1.5b, gemma2:2b, llama3.2:1b, phi3:mini,
           smollm2, qwen2.5vl (vision), gemma4:e2b (current default — the one
           too big for our hardware).
           SEED IDEA — everything else in the LLM section depends on it.

[ ] FE-019  OCR-hybrid pipeline (design done, needs code)              [P1][L]
           The design + prompts already live in tools/prompt-ocr-to-filename.md
           (tesseract OCR → tiny text-only model). Wire it into the app:
           pytesseract extraction, a "pipeline" setting (vision | ocr-hybrid |
           heuristic), and swap _call_ollama_suggest's payload accordingly.
           Solves the original roadblock: no vision model needed on-device.

[ ] FE-020  Model keep-alive / warm-start                             [P2][S]
           Ollama unloads idle models → every batch pays a cold-start. Set
           keep_alive on the /api/chat call (or pre-warm /api/generate),
           and surface "model still loading" instead of treating it as failure.

[ ] FE-021  Async suggestion queue                                    [P3][L]
           Server-side queue so suggest-batch doesn't block request-per-file;
           progress via SSE or polling. Frontend already has progress UI.

[ ] FE-022  Suggestion cache by content                               [P2][M]
           Memory store fingerprints by name|size today. Content hashing
           (sha256) would catch re-imported/renamed copies and reuse names —
           but costs one file read per screenshot. Measure before building.

[ ] FE-023  Fallback naming chain                                     [P2][M]
           LLM down → OCR-only name → heuristic (date/size) → "screenshot".
           The app degrades gracefully instead of failing closed. Complements
           the circuit breaker from #68.

[ ] FE-024  Auto-select best model per hardware                       [P3][S]
           Run FE-018's benchmark once, cache the winner in settings, done.

[ ] FE-025  MLX-native path (Apple Silicon GPU)                       [P2][L]
           If FE-018 shows MLX wins on quality/speed, add mlx-lm as an
           optional backend. Needs graceful fallback when no Metal GPU.


PRODUCT FEATURES (NO AI)
------------------------

[ ] FE-026  Stats dashboard                                           [P2][M]
           "You take 40 screenshots/week; 18% are duplicates; biggest week was
           June." Pure metadata + memory store — no ML. Great marketing story
           and genuinely useful.

[ ] FE-027  Watch folder (auto-refresh)                               [P2][M]
           fsmonitor/watchdog: new screenshots appear in the kanban live
           instead of needing a reload. The #1 "it feels alive" upgrade.

[ ] FE-028  Smart rules engine                                       [P2][M]
           If/then: "Screenshot from <app> older than 30 days → Trash",
           "bigger than 5MB → Keep". Rules run at launch; overrides manual
           sort. Reuses category logic already built in Phase 4.

[ ] FE-029  Screenshot clustering (FE-012's real form)                [P3][M]
           Group by source app via macOS metadata (kMDItemCreator /
           kMDItemWhereFroms) — macOS records the app that took the shot.

[ ] FE-030  Bulk rename patterns (FE-005)                             [P3][M]
           "vacation-YYYY-MM-DD-NNN" style batch renames. UI for pattern
           templates; preview before applying.

[ ] FE-031  Export decisions (CSV/JSON)                               [P3][S]
           Audit trail of what was kept/trashed/renamed — export button.
           Trivial to build on memory.json.

[ ] FE-032  Finder/menubar integration                                [P3][L]
           Menubar icon with live count + click-to-open; right-click "Sort
           with Screenshot Declutterer" via a Finder extension (unsigned =
           painful — park until packaged).

[ ] FE-033  Cross-machine decisions                                   [P3][L]
           Sync state/memory via iCloud Drive folder instead of ~/.ss-dcl.
           Low ROI for a single-user tool — parked.

PARKED / PROBABLY NOT
---------------------

- Windows/Linux port: send2trash is cross-platform but the Screenshot
  naming, macOS metadata, and Trash semantics are all Apple-specific.
  Not worth it for a personal tool.
- Vision-model-first LLM rename: the roadblock that started all this —
  kept only as the FE-018 baseline to beat.
- Mobile app: categorically no.
